** How to Contribute to FOSS
Contributing to Free and Open Source Software (FOSS) is one of the
fastest ways to become a better developer. You learn how real software
is built, collaborate with experienced developers, improve your Git
and debugging skills, and build a public portfolio of work.

The goal is not to immediately add major features. The goal is to
become a reliable contributor by making many small, high-quality
improvements.

*** Step 1 — Find a Project

Choose software that you actually use or find interesting.

Good places to look:

- GitHub "good first issue"
- goodfirstissue.dev
- up-for-grabs.net
- CodeTriage
- firstcontributions

Good beginner projects include:

- Emacs
- Helix
- Neovim
- Yazi
- fd
- ripgrep
- bat
- eza
- tmux
- Hyprland

*** Step 2 — Read Before Coding

Before writing code, spend time understanding the project.

Read:

- README
- CONTRIBUTING.md
- CODE_OF_CONDUCT.md
- Architecture documentation
- Existing issues
- Existing pull requests

Build the project locally and make sure all tests pass.

*** Step 3 — Understand the Codebase

Spend time exploring.

Questions to answer:

- Where is the entry point?
- How is the project organized?
- How are tests written?
- How are errors handled?
- What coding style is used?
- How are features added?

Don't rush this step.

*** Step 4 — Make Your First Contribution

Start extremely small.

Examples:

- Fix a typo
- Improve documentation
- Improve an example
- Improve an error message
- Fix formatting
- Add missing comments

Learning the workflow is more important than writing lots of code.

*** Step 5 — Create a Branch

Never work directly on the main branch.

Example:

- Create a feature branch
- Make one logical change
- Commit it with a descriptive message

Keep commits focused.

*** Step 6 — Test Everything

Before submitting:

- Build the project
- Run tests
- Run linters
- Format the code
- Read your changes again

Never assume your change works.

*** Step 7 — Open a Pull Request

A good pull request includes:

- What changed
- Why it changed
- Screenshots (if UI)
- Related issue number
- Testing performed

Keep pull requests small.

Small PRs are reviewed much faster than huge ones.

*** Step 8 — Respond to Review

Almost every pull request receives feedback.

Do not take review comments personally.

Instead:

- Ask questions
- Make requested changes
- Learn from suggestions
- Update the PR

Good contributors respond quickly and politely.

*** Step 9 — Repeat

The second contribution is easier.

The tenth is much easier.

Consistency matters far more than making one huge contribution.

Fewest key presses
Fewest interactive commands (M-x counts as one command)
Shortest keyboard macro
Shortest Elisp one-liner
Fastest completion time
