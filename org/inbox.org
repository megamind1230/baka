A *helper function* is a small function that exists to support another
function or class internally.

Usually:

- it does one tiny repeated task
- simplifies bigger methods
- improves readability
- is often =private=

--------------

** Without Helper Functions
:PROPERTIES:
:CUSTOM_ID: without-helper-functions
:END:
#+begin_src csharp
public void Register(string username, string password)
{
    if (string.IsNullOrWhiteSpace(username))
        throw new Exception("Invalid username");

    if (password.Length < 8)
        throw new Exception("Weak password");

    Console.WriteLine("User registered");
}
#+end_src

Works fine...

But imagine this validation logic appears in:

- Register
- Login
- ResetPassword
- UpdateProfile

Now you're duplicating code.

--------------

** With Helper Functions
:PROPERTIES:
:CUSTOM_ID: with-helper-functions
:END:
#+begin_src csharp
public void Register(string username, string password)
{
    ValidateUsername(username);
    ValidatePassword(password);

    Console.WriteLine("User registered");
}

private void ValidateUsername(string username)
{
    if (string.IsNullOrWhiteSpace(username))
        throw new Exception("Invalid username");
}

private void ValidatePassword(string password)
{
    if (password.Length < 8)
        throw new Exception("Weak password");
}
#+end_src

Now:

- cleaner
- reusable
- easier to debug
- easier to modify later

--------------

** Real-World Examples of Helper Functions
:PROPERTIES:
:CUSTOM_ID: real-world-examples-of-helper-functions
:END:
** Formatting
:PROPERTIES:
:CUSTOM_ID: formatting
:END:
#+begin_src csharp
private string FormatCurrency(decimal amount)
{
    return $"${amount:F2}";
}
#+end_src

--------------

** Validation
:PROPERTIES:
:CUSTOM_ID: validation
:END:
#+begin_src csharp
private bool IsEmailValid(string email)
{
    return email.Contains("@");
}
#+end_src

--------------

** Repeated Calculations
:PROPERTIES:
:CUSTOM_ID: repeated-calculations
:END:
#+begin_src csharp
private double CalculateTax(double price)
{
    return price * 0.14;
}
#+end_src

--------------

** UI Helpers
:PROPERTIES:
:CUSTOM_ID: ui-helpers
:END:
#+begin_src csharp
private void ShowError(string message)
{
    MessageBox.Show(message);
}
#+end_src

--------------

** Why They're Usually =private=
:PROPERTIES:
:CUSTOM_ID: why-theyre-usually-private
:END:
Because outside code should not care HOW your class works internally.

Users should do:

#+begin_src csharp
service.Register(...);
#+end_src

NOT:

#+begin_src csharp
service.ValidatePassword(...);
#+end_src

Validation is an internal detail.

--------------

** Mental Model
:PROPERTIES:
:CUSTOM_ID: mental-model
:END:
Think of helper functions as:

#+begin_quote
little workers behind the scenes helping the main feature work.
#+end_quote

Main method:

#+begin_src csharp
Checkout()
#+end_src

Helpers:

#+begin_src csharp
ValidateCart()
CalculateTotal()
ApplyDiscount()
SendReceipt()
#+end_src

--------------

** Good Sign You Need a Helper Function
:PROPERTIES:
:CUSTOM_ID: good-sign-you-need-a-helper-function
:END:
If you notice:

- repeated code
- huge methods
- deeply nested logic
- hard-to-read code

...extract part of it into a helper function.

--------------

** Common Beginner Mistake
:PROPERTIES:
:CUSTOM_ID: common-beginner-mistake
:END:
Making everything =public=.

Example:

#+begin_src csharp
public void CalculateTax()
#+end_src

If ONLY the class itself uses it → make it =private=.

Keep public APIs small and clean.

* emacs and how to navigate files/folders faster

If you're using Emacs regularly, there are several ways to make
=find-file= (=C-x C-f=) significantly better. The best setup depends on
whether you want speed, fuzzy matching, project awareness, or terminal
compatibility.

** 1. Vertico + Orderless + Marginalia (recommended)
This is the current "modern Emacs" stack.

*** Features
- Fast minibuffer completion
- Fuzzy-ish matching (=foo bar= matches anything containing both)
- Rich annotations (file size, permissions, etc.)
- Works great in terminal Emacs
- Uses built-in APIs

Install:

#+begin_src elisp
(use-package vertico
  :init
  (vertico-mode))

(use-package orderless
  :custom
  (completion-styles '(orderless basic)))

(use-package marginalia
  :init
  (marginalia-mode))
#+end_src

Optional:

#+begin_src elisp
(use-package consult)
(use-package embark)
#+end_src

Now =C-x C-f= becomes much nicer automatically.

--------------

** 2. Find files with project awareness
Instead of searching from the current directory:

#+begin_src elisp
(project-find-file)
#+end_src

Bind it:

#+begin_src elisp
(global-set-key (kbd "C-c p f") #'project-find-file)
#+end_src

or if you use Projectile:

#+begin_src elisp
(projectile-find-file)
#+end_src

This searches only inside the current Git/project.

--------------

** 3. Use Consult
Instead of =find-file=, use:

#+begin_src elisp
consult-find
#+end_src

or

#+begin_src elisp
consult-fd
#+end_src

if you have =fd= installed.

Example:

#+begin_example
M-x consult-fd
#+end_example

Instant fuzzy search over your project.

--------------

** 4. Install =fd=
=fd= is much faster than =find=.

Linux:

#+begin_src sh
sudo pacman -S fd
# or
sudo apt install fd-find
#+end_src

Then:

#+begin_src elisp
(setq consult-fd-args
      "fd --hidden --follow --exclude .git")
#+end_src

--------------

** 5. Enable recursive minibuffers
So you don't get stuck inside prompts.

#+begin_src elisp
(setq enable-recursive-minibuffers t)
(minibuffer-depth-indicate-mode)
#+end_src

--------------

** 6. Recent files
#+begin_src elisp
(recentf-mode 1)
(setq recentf-max-saved-items 500)
#+end_src

Open recent:

#+begin_src elisp
consult-recent-file
#+end_src

or

#+begin_src elisp
recentf-open-files
#+end_src

--------------

** 7. Save minibuffer history
#+begin_src elisp
(savehist-mode)
#+end_src

Now previous file names are remembered.

--------------

** 8. Better default directory navigation
Inside =find-file=:

- =M-DEL= deletes one directory component.
- =~= jumps to your home directory.
- =/ssh:user@host:= opens a remote file via TRAMP.
- =TAB= completes directory names.

--------------

** 9. Use fuzzy file search instead of path typing
Instead of typing:

#+begin_example
~/projects/foo/src/controllers/user_controller.cs
#+end_example

you can use =consult-fd= or =project-find-file= and type something like:

#+begin_example
user cont
#+end_example

or

#+begin_example
controller user
#+end_example

With Orderless, the space-separated terms can match in any order.

--------------

** 10. If you use Evil
Many users bind project file search to a leader key:

#+begin_src elisp
SPC f f   project-find-file
SPC f r   consult-recent-file
SPC /     consult-ripgrep
#+end_src

This gives a workflow similar to Neovim's Telescope.

--------------

** My recommended setup
For a fast, modern experience, I'd use:

- *Vertico* for minibuffer UI
- *Orderless* for flexible matching
- *Marginalia* for annotations
- *Consult* for enhanced commands
- *Embark* for context actions
- *=fd=* for fast file discovery
- Built-in *project.el* (or Projectile if you already use it)
- *recentf* and *savehist* enabled

This combination is lightweight, works well in both GUI and terminal
Emacs, and has become a popular replacement for older completion
frameworks like Helm and Ivy.

If your Avalonia app is already finished, making it plugin-friendly
usually means introducing a *plugin loading layer* without rewriting the
whole application.

** Option 1: Simple DLL Plugins (Recommended)
Create a contract assembly:

#+begin_src csharp
// MyApp.Plugin.Abstractions

public interface IPlugin
{
    string Name { get; }

    void Initialize(IPluginContext context);
}
#+end_src

Your main app references only =MyApp.Plugin.Abstractions=.

A plugin:

#+begin_src csharp
public class WordCountPlugin : IPlugin
{
    public string Name => "Word Count";

    public void Initialize(IPluginContext context)
    {
        context.RegisterCommand(
            "wordcount",
            () => Console.WriteLine("Counting words...")
        );
    }
}
#+end_src

At startup:

#+begin_src csharp
var pluginDir = Path.Combine(AppContext.BaseDirectory, "plugins");

foreach (var dll in Directory.GetFiles(pluginDir, "*.dll"))
{
    var asm = Assembly.LoadFrom(dll);

    foreach (var type in asm.GetTypes())
    {
        if (typeof(IPlugin).IsAssignableFrom(type) &&
            !type.IsInterface &&
            !type.IsAbstract)
        {
            var plugin = (IPlugin)Activator.CreateInstance(type)!;
            plugin.Initialize(context);
        }
    }
}
#+end_src

Directory:

#+begin_src text
MyApp/
├── MyApp.exe
├── plugins/
│   ├── WordCount.dll
│   ├── ExportHtml.dll
│   └── ThemeSolarized.dll
#+end_src

--------------

** Option 2: MEF (Managed Extensibility Framework)
Microsoft's plugin framework.

#+begin_src csharp
[Export(typeof(IPlugin))]
public class MyPlugin : IPlugin
{
}
#+end_src

Then discover automatically.

Pros:

- Less reflection code.

Cons:

- Feels somewhat heavy for smaller apps.

For a markdown/org renderer I'd skip MEF.

--------------

** Option 3: Dependency Injection Plugins
If you're already using:

#+begin_src csharp
Microsoft.Extensions.DependencyInjection
#+end_src

Plugins can register services:

#+begin_src csharp
public interface IPlugin
{
    void RegisterServices(IServiceCollection services);
}
#+end_src

Example:

#+begin_src csharp
plugin.RegisterServices(services);
#+end_src

Good when plugins provide:

- Renderers
- Commands
- Search providers
- Exporters

--------------

** Option 4: Separate Process Plugins
How browsers and IDEs often do it.

#+begin_src text
Main App
    |
    +---- Plugin Process
#+end_src

Communicate through:

- Named pipes
- gRPC
- JSON-RPC

Pros:

- Plugin crashes don't kill app.
- Better security.

Cons:

- Much more work.

Probably overkill for your renderer.

--------------

** Plugin Ideas for a Markdown/Org Renderer
Since your app is a *viewer/renderer*, not an editor:

1. PDF export
2. HTML export
3. EPUB export
4. Syntax highlighting themes
5. Mermaid diagrams
6. Graphviz diagrams
7. KaTeX/MathJax math rendering
8. PlantUML rendering
9. Table of Contents panel
10. Backlinks viewer
11. Wiki-style links (=[[Page]]=)
12. File attachment preview
13. Image gallery mode
14. Reading statistics
15. Citation/BibTeX support
16. RSS feed rendering
17. Org agenda viewer
18. Slideshow/presentation mode
19. Search index provider
20. Custom URI handlers (=note://=, =obsidian://=)

--------------

** Architecture I'd Use
For a markdown/org renderer:

#+begin_src csharp
public interface IPlugin
{
    string Name { get; }

    void Initialize(IPluginContext context);
}

public interface IRendererExtension
{
    bool CanRender(string blockType);

    Control Render(object block);
}

public interface ICommandProvider
{
    IEnumerable<AppCommand> Commands();
}

public interface IExporter
{
    string FormatName { get; }

    Task ExportAsync(Document doc);
}
#+end_src

Then plugins can contribute:

#+begin_src text
Plugin
 ├── Commands
 ├── Renderers
 ├── Exporters
 ├── Sidebar Panels
 └── Themes
#+end_src

This is very similar to how Visual Studio Code extensions work, but much
smaller and easier to maintain.

It depends on *how the application was published*. In .NET there are
several deployment modes, and they behave very differently.

** 1. Framework-Dependent Deployment (FDD)
#+begin_src sh
dotnet publish -c Release
#+end_src

Output:

#+begin_src text
MyApp.exe
MyApp.dll
MyApp.runtimeconfig.json
...
#+end_src

*** What gets included?
✅ Your application code

✅ NuGet libraries

❌ .NET runtime

❌ ASP.NET runtime (if needed)

❌ Desktop runtime (WPF/WinForms if needed)

*** End-user requirements
The user must already have the correct .NET runtime installed.

Example:

#+begin_src text
MyApp requires .NET 9 Desktop Runtime
#+end_src

If they don't have it:

#+begin_src text
You must install .NET to run this application
#+end_src

--------------

** 2. Self-Contained Deployment (SCD)
#+begin_src sh
dotnet publish -c Release -r win-x64 --self-contained true
#+end_src

Output size becomes much larger.

*** What gets included?
✅ Your application

✅ NuGet packages

✅ .NET runtime

✅ CoreCLR

✅ Garbage collector

✅ Everything required from .NET

*** End-user requirements
Nothing .NET-related.

The user can run:

#+begin_src text
MyApp.exe
#+end_src

on a clean Windows installation.

This is usually what people mean by:

#+begin_quote
"Bundle .NET with my application."
#+end_quote

--------------

** 3. Single-File Deployment
#+begin_src sh
dotnet publish -c Release -r win-x64 \
    --self-contained true \
    -p:PublishSingleFile=true
#+end_src

Output:

#+begin_src text
MyApp.exe
#+end_src

instead of dozens of files.

*** What gets included?
✅ App

✅ Runtime

✅ Libraries

✅ Most managed dependencies

*** End-user requirements
Typically none.

This is often the easiest distribution model.

--------------

** 4. Native AOT
#+begin_src sh
dotnet publish -c Release -r win-x64 \
    -p:PublishAot=true
#+end_src

Output:

#+begin_src text
MyApp.exe
#+end_src

*** What gets included?
The application is compiled ahead-of-time into native machine code.

Advantages:

- Faster startup
- Smaller memory usage
- No .NET runtime needed

Disadvantages:

- Some reflection-heavy libraries may not work.
- Not every project can use AOT.

--------------

** Non-.NET Dependencies
This is where many developers get surprised.

** Case A: Pure NuGet Packages
Example:

#+begin_src xml
<PackageReference Include="Newtonsoft.Json" />
#+end_src

or

#+begin_src xml
<PackageReference Include="Markdig" />
#+end_src

These are automatically included.

The user does not install them.

--------------

** Case B: Native DLLs
Example:

#+begin_src text
sqlite3.dll
libgit2.dll
opencv.dll
ffmpeg.dll
#+end_src

Usually these get copied into the publish directory automatically if the
package is configured correctly.

Example publish output:

#+begin_src text
MyApp.exe
sqlite3.dll
#+end_src

The user only needs the publish folder.

--------------

** Case C: External Programs
Suppose your application calls:

#+begin_src csharp
Process.Start("git")
#+end_src

or

#+begin_src csharp
Process.Start("ffmpeg")
#+end_src

*** Git example
If you expect:

#+begin_src text
git.exe
#+end_src

to exist on the machine, then:

❌ It is not bundled automatically.

User must install Git.

--------------

*** FFmpeg example
If you ship:

#+begin_src text
ffmpeg.exe
#+end_src

inside your application folder,

then:

✅ User doesn't need to install FFmpeg separately.

You are distributing it with your app.

--------------

** Windows Runtime Dependencies
Even self-contained apps may still rely on things Windows normally
provides.

Examples:

- Windows kernel
- User32.dll
- GDI32.dll
- DirectX
- Visual C++ Redistributable (rare nowadays with modern .NET, but some
  native libraries still need it)

These are operating system dependencies, not .NET dependencies.

--------------

** How to Check What Your Users Need
After publishing:

Create a fresh Windows VM.

For example:

- Windows 10
- No Visual Studio
- No .NET SDK
- No runtimes

Copy only:

#+begin_src text
publish/
#+end_src

Run:

#+begin_src text
MyApp.exe
#+end_src

If it works:

✅ Everything is bundled.

If it fails:

❌ You're missing a dependency.

This is the most reliable test.

If you're building an Avalonia desktop application and want the simplest
distribution:

#+begin_src sh
dotnet publish -c Release \
-r win-x64 \
--self-contained true \
-p:PublishSingleFile=true

If you're in an Emacs buffer with Markdown (or any text with =*=
headings), there are several ways to jump between headings without
moving line by line.

*** If you're using =outline-mode= or =outline-minor-mode=
These are the standard commands:

- =C-c C-n= → next heading
- =C-c C-p= → previous heading
- =C-c C-f= → next heading at the same level
- =C-c C-b= → previous heading at the same level
- =C-c C-u= → parent heading

You can enable it with:

#+begin_src elisp
M-x outline-minor-mode
#+end_src

or if you're in Markdown, it may already be available.

--------------

*** If you're using =markdown-mode=
=markdown-mode= has its own navigation:

- =C-c C-n= → next heading
- =C-c C-p= → previous heading
- =C-c C-f= → forward same-level heading
- =C-c C-b= → backward same-level heading
- =C-c C-u= → up one heading

These are usually the most convenient.

--------------

*** Jump to any heading
For large files:

#+begin_example
M-x imenu
#+end_example

or bind it to a key.

If you use packages like *Consult* or *Helm*:

#+begin_example
consult-imenu
#+end_example

or

#+begin_example
helm-imenu
#+end_example

lets you fuzzy-search all headings instantly.

--------------

*** If your file uses Org-style headings (=* Heading=)
In =org-mode=:

- =C-c C-n= → next heading
- =C-c C-p= → previous heading
- =C-c C-f= → next sibling
- =C-c C-b= → previous sibling
- =C-c C-u= → parent

--------------

*** My recommendation
If your files are Markdown with =#= headings, use =markdown-mode='s
built-in navigation.

If your files literally use =* Heading= syntax (Org-style), use
=org-mode=---its navigation is exceptionally fast and designed for this
workflow.
