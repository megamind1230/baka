* DONE what is helper function in csharp
A *helper function* is a small function that
exists to support another function or class internally.
(a crucial repeative part of some functions)

** Why They're Usually =private=
Because outside code should not care HOW your class works internally.

Users should do:

#+begin_src csharp

  service.Register(...);
#+end_src
NOT:
#+begin_src csharp

  service.ValidatePassword(...);
#+end_src
Validation is an internal detail.
** Mental Model
Think of helper functions as:
little workers behind the scenes helping the main feature work.

- Main method: Checkout()
- Helpers:
    ValidateCart()
    CalculateTotal()
    ApplyDiscount()
    SendReceipt()

** when to use?
If you notice:
- repeated code
- huge methods
- deeply nested logic
- hard-to-read code
* DONE acid db meaning
*ACID* = atomicity, consistency, isolation, durability
A *transaction* is a group of operations that should be treated as a
single unit: all or nothing

** Easy way to remember
| Letter | Meaning     | Simple phrase                   |
|--------+-------------+---------------------------------|
| *A*    | Atomicity   | All or nothing                  |
| *C*    | Consistency | Rules are never broken          |
| *I*    | Isolation   | Transactions don't interfere    |
| *D*    | Durability  | Committed data survives crashes |
*** One-line mnemonic
*A*ll or nothing, *C*orrect state, *I*ndependent transactions, *D*ata
lasts forever (after commit).
** A --- Atomicity
*All or nothing.*
Either every step succeeds, or every step is undone.
** C --- Consistency
#+begin_quote
The database always moves from one valid state to another valid state.
#+end_quote
Rules (constraints) must always remain true.
Example:
Bank rule:
#+begin_example
Total money cannot change
#+end_example
Before transfer: total = 1600
#+begin_example
    Alice = 500
    Bob   = 300
    Total = 800
#+end_example
After transfer: total = 1600
#+begin_example
    Alice = 400
    Bob   = 400
    Total = 800
#+end_example
Consistent.
Another example: #baka
Table:
#+begin_example
Students
Id
Name
Age CHECK (Age >= 0)
#+end_example
Trying to insert
#+begin_example
Age = -5
#+end_example
fails because it violates a constraint.
Consistency means:
- Foreign keys stay valid.
- Primary keys remain unique.
- CHECK constraints hold.
- Business rules are preserved.
** I --- Isolation
#+begin_quote
Transactions don't interfere with each other.
#+end_quote
Imagine two ATMs withdrawing from the same account simultaneously.
Without isolation:
#+begin_example
Balance = 100
ATM 1 reads 100
ATM 2 reads 100
ATM 1 withdraws 80
ATM 2 withdraws 80
Final balance = 20
#+end_example
But $160 was withdrawn!
With isolation, transactions behave as if they run one after another (or
otherwise produce a result equivalent to a valid serial execution,
depending on the isolation level).
Possible execution:
#+begin_example
Balance = 100
ATM 1
withdraw 80
Balance = 20
ATM 2
cannot withdraw 80
#+end_example
Isolation prevents problems like:
- Dirty reads
- Non-repeatable reads
- Phantom reads
Databases provide different *isolation levels* (e.g., Read Committed,
Repeatable Read, Serializable) that balance correctness and performance.
** D --- Durability
Once committed, data is permanent.
Suppose:
#+begin_example
Transfer completed
COMMIT;
#+end_example
Immediately afterward:
#+begin_example
Power outage
#+end_example
After restarting the database:
#+begin_example
Transfer is still there.
#+end_example
The database stores committed changes in persistent storage (such as
transaction logs and disk), so they survive crashes.
** mega example
Imagine buying an item online:
#+begin_example
1. Deduct money
2. Reduce stock
3. Create order
4. Send confirmation
#+end_example
If step 3 fails:
*Atomicity*
#+begin_example
Undo 1 and 2.
#+end_example
*Consistency*
#+begin_example
Money and inventory remain correct.
#+end_example
*Isolation*
#+begin_example
Other customers don't see half-completed updates or interfere with your transaction.
#+end_example
*Durability*
#+begin_example
After the order is committed, it won't disappear even if the server crashes.
#+end_example
* DONE logging vs debugging vs unit testing in csharp
These three are complementary but solve different problems.
| Tool           | Purpose                            | When Used                         | Finds                              |
|----------------+------------------------------------+-----------------------------------+------------------------------------|
| *Logging*      | Record what happened               | During development and production | Runtime events                     |
| *Debugging*    | Investigate why something is wrong | During development                | Logic bugs                         |
| *Unit Testing* | Verify code behaves correctly      | Before and after changes          | Regressions and incorrect behavior |
** DONE 1. Logging
Logging is writing information about your program while it runs.
Typical things to log:
- User logged in
- HTTP request received
- Database query failed
- File uploaded
- Unexpected exception
- Execution time
C# Example
#+begin_src csharp
using Microsoft.Extensions.Logging;
public class UserService
{
    private readonly ILogger<UserService> _logger;
    public UserService(ILogger<UserService> logger)
    {
        _logger = logger;
    }
    public void Login(string username)
    {
        _logger.LogInformation("User {User} logged in.", username);
    }
}
#+end_src
Output: [Information] User Hassan logged in.
Common log levels
    Trace
    Debug
    Information
    Warning
    Error
    Critical
Use logging when asking: "What happened?"
** DONE 2. Debugging
Debugging means running the program under
a debugger so you can inspect it.
You use:
- Breakpoints
- Step Into (F11)
- Step Over (F10)
- Call Stack
- Watch Window
- Locals
Use debugging when asking: "Why did this happen?"
** DONE 3. Unit Testing
Unit tests automatically verify that code works.
Suppose you wrote:
#+begin_src csharp
public int Add(int a, int b)
{
    return a + b;
}
#+end_src
An xUnit test:
#+begin_src csharp
using Xunit;
public class CalculatorTests
{
    [Fact]
    public void Add_ReturnsCorrectSum()
    {
        var calc = new Calculator();
        Assert.Equal(5, calc.Add(2, 3));
    }
}
#+end_src
Running tests: ✔ Add_ReturnsCorrectSum
If you accidentally change the method to subtract: return a - b;
the test fails immediately.
Use unit tests when asking: "Does my code still work?"
** DONE Real-world Example
Imagine you're building an ASP.NET Core Todo API.
> Logging
#+begin_src text
INFO  User 42 requested GET /todos
INFO  Retrieved 15 todos
#+end_src
Later:
#+begin_src text
ERROR Database connection timed out
#+end_src
Logs help you understand what happened in production.

> Debugging
While developing, you notice a new todo isn't being saved.
You:
- Set a breakpoint in =CreateTodo()=
- Inspect the request object
- Step through Entity Framework
- Find that =Title= is =null=
Fix the bug.

> Unit Testing
You write tests like:
#+begin_src text
CreateTodo_ShouldStoreTodo()
DeleteTodo_ShouldRemoveTodo()
GetTodo_ShouldReturnTodo()
#+end_src
Later, after refactoring, all tests still pass, giving you confidence
you didn't break existing behavior.
** DONE In Modern C# Development
A typical workflow is:
1. Write code.
2. Write and run unit tests.
3. Debug if test fails.
4. logging around important operations.
5. Deploy.
6. Use logs to diagnose production issues.
