*** ✅ Simple meaning of /Unit Testing/
:PROPERTIES:
:CUSTOM_ID: simple-meaning-of-unit-testing
:END:
*Unit testing = testing small pieces of your code (units) to make sure
each one works correctly.*
- A /unit/ is usually a *method/function*
- You test it *independently* from the rest of the program
👉 Think of it like:
#+begin_quote
Instead of testing the whole car, you test the *engine alone*, then the
*brakes alone*, etc.
#+end_quote
--------------
*** 💡 Why it matters
:PROPERTIES:
:CUSTOM_ID: why-it-matters
:END:
- Finds bugs early 🐛
- Makes your code safer to change
- Helps you understand your own code better
--------------
*** 🧠 Simple C# example
:PROPERTIES:
:CUSTOM_ID: simple-c-example
:END:
Let's say you wrote this method:
#+begin_src csharp
public int Add(int a, int b)
{
    return a + b;
}
#+end_src
A *unit test* checks if it works correctly:
#+begin_src csharp
[Test]
public void Add_ShouldReturnCorrectSum()
{
    int result = Add(2, 3);
    Assert.AreEqual(5, result);
}
#+end_src
👉 This test says:
- Call =Add(2, 3)=
- Expect the result to be =5=
--------------
*** 🧰 Tools in C# (very common)
:PROPERTIES:
:CUSTOM_ID: tools-in-c-very-common
:END:
You usually use frameworks like:
- NUnit
- xUnit
- MSTest
They provide:
- =[Test]= → marks a test
- =Assert= → checks results
--------------

:CUSTOM_ID: can-you-do-a-simple-project-yes-good-idea
:END:
Start small. Example project:
**** 🧮 "Calculator with tests"

1. Create methods:

2. [@2] Write tests for each:
#+begin_src csharp
[Test]
public void Divide_ByZero_ShouldThrowError()
{
    Assert.Throws<DivideByZeroException>(() => Divide(5, 0));
}
#+end_src
--------------
*** 🔑 Key concepts (easy terms)
:PROPERTIES:
:CUSTOM_ID: key-concepts-easy-terms
:END:
- *Test case* → one check (e.g., 2+3=5)
- *Assert* → verify result
- *Test suite* → group of tests
- *Pass/Fail* → result of test
--------------

- Your app = big machine
- Unit tests = small inspectors checking each part

* NEXT what is mcp?
** MCP, simply explained
*MCP* usually means *Model Context Protocol*.
The simplest explanation:
#+begin_quote
*MCP is a standard way for an AI to use external tools and data.*
#+end_quote
Imagine ChatGPT is a person sitting at a desk.
Without MCP:
#+begin_src text
AI
 │
 ├── Can talk
 ├── Can reason
 └── Cannot directly interact with your tools
#+end_src
With MCP:
#+begin_src text
                 ┌── Files
                 ├── Database
AI ── MCP ───────┼── GitHub
                 ├── Calendar
                 └── Your own application
#+end_src
MCP gives the AI a *standard language for interacting with external
systems*.
** Level 1: The simplest example
Imagine you tell an AI:
#+begin_quote
"What files are in my project?"
#+end_quote
The AI itself does not magically know your filesystem.
An MCP server can provide a tool:
#+begin_src text
list_files()
#+end_src
The AI can call it:
#+begin_src text
AI
 │
 │ "I need to see the files"
 ▼
MCP tool: list_files()
 │
 ▼
project/
├── Program.cs
├── README.md
└── src/
#+end_src
Then the AI can answer:
#+begin_quote
"Your project contains =Program.cs=, =README.md=, and a =src=
directory."
#+end_quote
The important thing:
#+begin_src text
AI
  ↓
MCP
  ↓
Tool
  ↓
External data/action
#+end_src
** Level 2: MCP is like USB for AI
A useful analogy:
**** Before USB
Every device needed a different connector:
#+begin_src text
Keyboard ── special connector
Mouse ───── different connector
Printer ─── another connector
#+end_src
USB standardized the connection.
#+begin_src text
Computer
   │
   └── USB
       ├── Keyboard
       ├── Mouse
       ├── Printer
       └── Storage
#+end_src
MCP tries to do something similar for AI:
#+begin_src text
AI application
      │
      └── MCP
          ├── Filesystem
          ├── GitHub
          ├── Database
          ├── Calendar
          └── Custom application
#+end_src
Instead of every AI application needing a completely different
integration for every tool, they can communicate through a common
protocol.
** Level 3: MCP servers and clients
MCP has two important sides.
*** The MCP client
This is the AI application.
Examples conceptually:
#+begin_src text
Claude Desktop
ChatGPT
An IDE
Your own AI application
#+end_src
The client connects to MCP servers.
#+begin_src text
┌──────────────────┐
│   AI Application │
│   MCP Client     │
└────────┬─────────┘
         │
         │ MCP
         ▼
┌──────────────────┐
│   MCP Server     │
└──────────────────┘
#+end_src
*** The MCP server
The server exposes capabilities.
For example:
#+begin_src text
Filesystem MCP Server
├── read_file
├── write_file
├── list_directory
└── search_files
#+end_src
Or:
#+begin_src text
Database MCP Server
├── list_tables
├── describe_table
└── execute_query
#+end_src
Or:
#+begin_src text
GitHub MCP Server
├── list_repositories
├── search_code
├── create_issue
└── read_pull_request
#+end_src
The AI does not need to know the internal implementation.
It only needs to know:
#+begin_src text
Tool name: search_files
Input: query
Output: matching files
#+end_src
** Level 4: Tools, resources, and prompts
MCP servers can expose several kinds of things.
*** 1. Tools
Tools are actions the AI can invoke.
Example:
#+begin_src text
search_files(query)
#+end_src
The AI:
#+begin_src text
search_files("DbContext")
#+end_src
The server:
#+begin_src text
[
  "src/AppDbContext.cs",
  "src/Program.cs"
]
#+end_src
Another example:
#+begin_src text
create_issue(
    title="Bug: Login fails",
    body="..."
)
#+end_src
The server performs the action.
*** 2. Resources
Resources are data the AI can read.
For example:
#+begin_src text
file:///project/README.md
#+end_src
or:
#+begin_src text
database://users
#+end_src
Conceptually:
#+begin_src text
AI
 │
 ├── "Read the README"
 │
 ▼
MCP Resource
 │
 ▼
README.md contents
#+end_src
The difference is roughly:
#+begin_src text
Tool      → do something
Resource  → access something
#+end_src
*** 3. Prompts
MCP can also expose reusable prompt templates.
For example:
#+begin_src text
review_code
#+end_src
might generate:
#+begin_src text
Review this code for:
1. Bugs
2. Security problems
3. Performance issues
4. Maintainability
#+end_src
The AI can use the predefined prompt.
** Level 5: A practical example: your code project
Imagine you have this project:
#+begin_src text
TaskManagementApi/
├── Core/
├── Infrastructure/
├── Api/
└── Tests/
#+end_src
You create an MCP server that exposes:
#+begin_src text
list_project_files()
read_file(path)
search_code(query)
run_tests()
#+end_src
Now you can ask an AI:
#+begin_quote
"Find all places where =TaskStatus= is used."
#+end_quote
The AI might do:
#+begin_src text
search_code("TaskStatus")
#+end_src
The MCP server runs:
#+begin_src sh
rg "TaskStatus" .
#+end_src
and returns:
#+begin_src text
Core/Entities/TaskStatus.cs
Api/Controllers/TasksController.cs
Tests/TaskTests.cs
#+end_src
Then you say:
#+begin_quote
"Why is there an ambiguity with System.Threading.Tasks.TaskStatus?"
#+end_quote
The AI can read:
#+begin_src text
Core/Entities/TaskStatus.cs
#+end_src
and inspect the relevant code.
The AI is now using your development environment through a standardized
interface.
** Level 6: MCP versus an API
Suppose you have a weather service.
Without MCP:
#+begin_src text
Your AI
   │
   └── custom HTTP code
        │
        ▼
     Weather API
#+end_src
You need to manually write integration code.
With MCP:
#+begin_src text
AI Application
      │
      ▼
MCP Client
      │
      ▼
Weather MCP Server
      │
      ▼
Weather API
#+end_src
The MCP server handles the API details.
The AI sees something like:
#+begin_src text
get_weather(city)
#+end_src
The implementation could internally be:
#+begin_src text
HTTP request
Authentication
JSON parsing
Error handling
Rate limiting
#+end_src
The AI doesn't need to know all of that.
** Level 7: MCP is not the AI
This is an important distinction.
MCP is *not*:
#+begin_src text
MCP = AI model
#+end_src
Instead:
#+begin_src text
┌─────────────────────┐
│     AI Model        │
│                     │
│ "I need to search"  │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│    MCP Client       │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│    MCP Server       │
│                     │
│  search_files()     │
└──────────┬──────────┘
           │
           ▼
       Filesystem
#+end_src
The AI reasons.
The MCP server provides capabilities.
** Level 8: Why MCP became useful
Before standardized protocols, every AI application might implement
integrations separately:
#+begin_src text
AI App A ── custom GitHub integration
AI App A ── custom database integration
AI App B ── different GitHub integration
AI App B ── different database integration
AI App C ── another GitHub integration
#+end_src
This creates a lot of duplicated work.
MCP aims for:
#+begin_src text
                  ┌── MCP GitHub Server
AI App A ────────┤
AI App B ────────┤
AI App C ────────┘
#+end_src
One server can potentially be used by multiple MCP-compatible clients.
** Level 9: An MCP server in code
Conceptually, an MCP server might define:
#+begin_src text
Tool: get_user
Input:
{
    "user_id": 42
}
Output:
{
    "name": "Hassan",
    "tasks": 12
}
#+end_src
The AI decides:
#+begin_quote
"I need information about user 42."
#+end_quote
It requests:
#+begin_src text
get_user(user_id=42)
#+end_src
The MCP server:
#+begin_src text
1. Receives request
2. Queries database
3. Gets result
4. Returns structured data
#+end_src
#+begin_src text
AI ◄──────────────► MCP Server ◄──────────────► Database
#+end_src
** Level 10: MCP versus function calling
You may already know about *function calling*.
For example, an AI model can be given:
#+begin_src json
{
  "name": "get_weather",
  "description": "Get weather information",
  "parameters": {
    "city": "string"
  }
}
#+end_src
The AI generates:
#+begin_src json
{
  "name": "get_weather",
  "arguments": {
    "city": "Cairo"
  }
}
#+end_src
That's function/tool calling.
MCP provides a *standardized ecosystem around this idea*.
Roughly:
#+begin_src text
Function calling:
    AI → specific tool
MCP:
    AI application
       ↓
    standardized protocol
       ↓
    discoverable server
       ↓
    tools/resources/prompts
#+end_src
So MCP is not exactly the same thing as function calling.
A useful analogy:
#+begin_src text
Function calling = individual function
MCP = standardized system for discovering and using many tools
#+end_src
** Level 11: MCP and your Emacs workflow
Imagine an MCP server for your Emacs environment.
The AI could have tools like:
#+begin_src text
emacs_open_file(path)
emacs_search(query)
emacs_eval_elisp(code)
emacs_current_buffer()
#+end_src
Then you could say:
#+begin_quote
"Find every TODO related to Emacs in my Org files."
#+end_quote
The AI could:
#+begin_src text
search_files(
    directory="~/org",
    query="TODO.*Emacs"
)
#+end_src
Then:
#+begin_quote
"Open the most relevant one."
#+end_quote
#+begin_src text
emacs_open_file(
    "~/org/emacs.org"
)
#+end_src
Or:
#+begin_quote
"Create an Org TODO for learning Embark."
#+end_quote
The MCP server could add:
#+begin_src org
,* TODO Learn Embark
#+end_src
to your Org file.
That is the basic idea of connecting an AI to your actual environment.
** Level 12: The security problem
This is where things become serious.
An MCP server may expose powerful capabilities:
#+begin_src text
read_file()
write_file()
delete_file()
run_command()
#+end_src
If an AI has:
#+begin_src text
run_command(command)
#+end_src
then theoretically it could run:
#+begin_src sh
rm -rf ~/important-data
#+end_src
Therefore:
#+begin_quote
*MCP servers should be treated like programs with permissions.*
#+end_quote
A safer design might expose:
#+begin_src text
read_project_file(path)
#+end_src
but not:
#+begin_src text
run_any_shell_command(command)
#+end_src
Or restrict paths:
#+begin_src text
Allowed:
~/projects/my-project/
Denied:
~/.ssh/
~/passwords/
#+end_src
The security model matters enormously.

#+begin_src elisp

#+end_src
tells =Consult=: When I use =consult-fd=, run =fd= with these options.

**** =--hidden=
Search hidden files too:
#+begin_src text
.gitignore
.config/
.env
#+end_src
Normally =fd= ignores hidden files.

**** =--follow=
Follow symbolic links.
For example:
#+begin_src text
project/
└── shared -> /home/dt/shared/
#+end_src
=fd= can follow that link and search inside =shared=.

**** =--exclude .git=
Do not search inside =.git=.
This is important because =.git= can contain a huge amount of internal
data that you usually don't want to search.
So:
#+begin_src elisp
(setq consult-fd-args
      "fd --hidden --follow --exclude .git")
#+end_src
means: Search hidden files, follow symlinks, but ignore Git's internal
directory. You can test the equivalent command directly in your
terminal:

#+begin_src sh
fd --hidden --follow --exclude .git
#+end_src

*** What does "recursive minibuffer" mean?
Imagine you are already inside a minibuffer:
#+begin_src text
Find file: _
#+end_src
Now you want to run another command that itself needs a minibuffer.
Normally, Emacs may prevent this or make it awkward.

With:
#+begin_src elisp
(setq enable-recursive-minibuffers t)
#+end_src
you can enter another minibuffer while already inside one.

For example:
#+begin_src text
Find file: /home/dt/...
#+end_src
While still in that prompt, you can invoke another minibuffer command.

This is especially useful with packages such as:
- =consult=
- =embark=
- =vertico=
- =orderless=
- =marginalia=
You can think of it as:
#+begin_src text
Minibuffer level 1
└── Minibuffer level 2
    └── Minibuffer level 3
#+end_src

*** What does this do?
#+begin_src elisp
(minibuffer-depth-indicate-mode)
#+end_src
It tells you how deeply nested you are.

For example:
#+begin_src text
[2] Find file:
#+end_src
means you are currently inside minibuffer level 2.
It is mostly a visual aid.

For a comfortable coding experience:
#+begin_src elisp
(setq scroll-conservatively 101
      scroll-margin 5
      scroll-preserve-screen-position t)
#+end_src
This gives you:
#+begin_src text
┌────────────────────┐
│                    │
│                    │
│                    │
│      cursor        │
│                    │
│                    │
│                    │
└────────────────────┘
#+end_src
The cursor will generally remain in a stable position instead of
constantly jumping to the top or bottom.
** If you want the cursor EXACTLY in the middle
You can bind scrolling keys to =recenter-top-bottom=.
For example:
#+begin_src elisp
(defun dt/scroll-down-centered ()
  "Scroll down and keep point near the center."
  (interactive)
  (scroll-up-command)
  (recenter))
(defun dt/scroll-up-centered ()
  "Scroll up and keep point near the center."
  (interactive)
  (scroll-down-command)
  (recenter))
#+end_src
Then:
#+begin_src elisp
(global-set-key (kbd "C-d") #'dt/scroll-down-centered)
(global-set-key (kbd "C-u") #'dt/scroll-up-centered)
#+end_src
Now:
#+begin_src text
C-d
#+end_src
scrolls down and centers the cursor.
#+begin_src text
C-u
#+end_src
scrolls up and centers the cursor.
With Evil, you could use:
#+begin_src elisp
(with-eval-after-load 'evil
  (define-key evil-normal-state-map (kbd "C-d")
    #'dt/scroll-down-centered)
  (define-key evil-normal-state-map (kbd "C-u")
    #'dt/scroll-up-centered))
#+end_src
** The package solution: =centered-cursor-mode=
There is also a package specifically designed for this.
Conceptually:
#+begin_src text
Normal Emacs:
┌──────────────┐
│              │
│              │
│              │
│              │
│              │
│              │
│ cursor       │
└──────────────┘
Centered cursor:
┌──────────────┐
│              │
│              │
│              │
│    cursor    │
│              │
│              │
│              │
└──────────────┘
#+end_src
The package is commonly used as:
#+begin_src elisp
(centered-cursor-mode 1)
#+end_src
or globally:
#+begin_src elisp
(global-centered-cursor-mode 1)
#+end_src
This is probably closest to what you are describing.
** For your setup, I would start here
Since you use *Evil mode*, try:
#+begin_src elisp
(setq scroll-conservatively 101
      scroll-preserve-screen-position t)
(with-eval-after-load 'evil
  (define-key evil-normal-state-map (kbd "C-d")
    (lambda ()
      (interactive)
      (evil-scroll-down nil)
      (recenter)))
  (define-key evil-normal-state-map (kbd "C-u")
    (lambda ()
      (interactive)
      (evil-scroll-up nil)
      (recenter)))
#+end_src
But there is an even simpler Evil-native option:
#+begin_src text
C-d
#+end_src
scrolls down.
#+begin_src text
C-u
#+end_src
scrolls up.
Then press:
#+begin_src text
zz
#+end_src
to center the cursor.
So your workflow becomes:
#+begin_src text
C-d
zz
#+end_src
or:
#+begin_src text
C-u
zz
#+end_src
In Vim/Evil terms:
#+begin_src text
zz = center current line on screen
zt = move current line to top
zb = move current line to bottom
#+end_src
